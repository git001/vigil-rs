# Contributing to vigil-rs

Thanks for helping! This page covers how to build and test vigil-rs, the
files that are generated from the code, and the conventions the project
follows.

## Workspace

| Crate | What it is |
|---|---|
| `crates/vigild` | The daemon: plan, overlord, service and check actors, HTTP API |
| `crates/vigil` | The CLI client |
| `crates/vigil-log-relay` | Forwards log streams (vigild, Kubernetes pods) to a TCP sink |
| `crates/vigil-types` | Types shared by all of them: layer files, API requests and responses |
| `crates/vigil-tls` | TLS material: CA bundles, certificate and key, HTTPS client settings |
| `crates/vigil-files` | Reading the files a configuration names: secrets, env files, certificates |

You need Rust 1.88 or newer. Static (musl) builds need extra tools; see [docs/user-guide/installation.md](docs/user-guide/installation.md).

## Checks

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs these three
commands. Run them before you open a pull request:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Fix clippy warnings in the code; do not silence them with
`#[allow(clippy::…)]`.

## Integration tests

- **VTest2** (`tests/vtest/`): end-to-end tests that start real vigild, vigil
  and vigil-log-relay processes. Run them with `tests/vtest/run.sh`.
  [tests/vtest/README.md](tests/vtest/README.md) explains the setup, lists
  every test and collects the patterns that work (native VTest2 clients
  first, static fixtures, no inline configs).
- **Kubernetes** (`tests/k8s/relay.sh`): tests `vigil-log-relay --kubernetes`
  against a real cluster. It needs `KUBECONFIG` and creates (and removes) the
  namespace `vigil-relay-test`.
- **Coverage**: `tests/vtest/run.sh --coverage` combines unit, integration
  and VTest2 coverage.

A bug fix comes with a test that fails without the fix.

## Generated files

Some files are generated. Do not edit them by hand.

### `docs/specs/openapi.yaml`

The OpenAPI spec is generated from `ApiDoc` in
[crates/vigild/src/api/openapi.rs](crates/vigild/src/api/openapi.rs), the
same object vigild serves at `/openapi.json`. utoipa builds it from the
`#[utoipa::path(...)]` attributes of the handlers in
`crates/vigild/src/api/handlers/` and the `ToSchema` types in `vigil-types`.

The unit test `openapi_yaml_is_up_to_date` renders `ApiDoc` as YAML and
compares it with the file, so `cargo test` fails when they differ. After you
change a handler's parameters, responses or description, or an API type,
regenerate the file and commit it with your change:

```sh
UPDATE_OPENAPI=1 cargo test -p vigild openapi_yaml
```

### Diagrams

The Graphviz sources `docs/**/*.dot` are rendered to `images/*.svg` by
[.github/workflows/diagrams.yml](.github/workflows/diagrams.yml), which
commits the SVGs to the same branch. Edit only the `.dot` files.

### `CHANGELOG.md`

The changelog is generated by [git-cliff](https://git-cliff.org/) from the
commit messages ([cliff.toml](cliff.toml)) when a release is made. Write good
commit messages instead of editing it.

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): summary`, for example `fix(api): …` or `feat(relay): …`.
Common types are `feat`, `fix`, `docs`, `test`, `refactor` and `chore`.

A change that breaks existing setups, scripts or API clients is marked with
`!` and explains the migration in a `BREAKING CHANGE:` footer. The footer goes
into the changelog as it is, so write it for users:

```
fix(api)!: reject unknown query parameters on /v1/logs/follow

BREAKING CHANGE: GET /v1/logs/follow answers 400 for an unknown query
parameter instead of ignoring it. Migration: use only `services` and
`format`.
```

Sign off your commits (`git commit -s`).

## Conventions

- **Strict configuration.** An unknown key or invalid value in a layer file
  is an error that names the key. Never ignore it silently.
- **Every option has an environment variable.** Each option of vigild,
  vigil-log-relay and the global options of `vigil` can also be set from the
  environment, so containers need no wrapper scripts. Boolean variables take
  `true` or `false`. Arguments of single `vigil` commands are the exception.
- **Unprivileged containers.** Every feature must work under OpenShift's
  restricted profile: a random UID, no capabilities, a read-only `/run`.
  Runtime files go under `--path-prefix`.
- **API errors.** Handlers check the caller's access before they look at
  the query or the body, and every error uses the JSON error envelope.
- **Small files.** Keep source files at about 200 lines (without tests);
  split a module when it grows past that.
- **English** for code, comments, docs and commit messages.
- **Docs follow the code.** A change to behaviour, options or the API
  updates `docs/` in the same pull request.
